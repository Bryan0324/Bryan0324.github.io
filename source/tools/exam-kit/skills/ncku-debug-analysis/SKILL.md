# S10｜邏輯分析與 Debug

## 工作契約

- 固定題目契約、可改範圍與一筆失敗案例；區分症狀、證據、假設與已確認原因。
- 考場的命令與測試由使用者執行。不能把靜態推導或建議的測試寫成實測通過。
- 不修改唯讀驗收器、預期答案、介面或輸入規格來讓測試通過；一次只修一個有證據的原因。

## 步驟

1. 收集目前版本、執行位置與命令、最小輸入、預期及其依據、實際輸出／traceback。若缺資料，先問最能區分原因的一項。
2. 沿「輸入→驗證→分支／迴圈→狀態更新→輸出」對照，定位第一個已知偏離契約的位置。崩潰行不一定是根因；資料可能更早被寫壞。
3. 檢查邊界、單位、型別／範圍、提前返回、初始化與跨次狀態、別名／副作用、錯誤處理、完成與生命週期。只分析與本案證據相關的項目。
4. 原因已由程式與反例確定時，直接給最小修改。否則最多列三個候選，各附支持／反證與缺漏，選一個能區分候選的觀察，寫明插入點及 A/B 結果意義。
5. 只輸出需要替換的函式或精確區塊，保留呼叫介面與允許範圍，解釋如何修復根因。
6. 重跑原失敗輸入，再測相關邊界與已通過案例；跨次狀態要在同進程連續呼叫。分開列已驗證與待驗證；兩次無效修改後回到最後可用版本重新定位。

## 固定輸出

1. 症狀、預期與第一個偏離點。
2. 已確認根因，或最多三個附證據的候選。
3. 一個最小修正或診斷動作，附執行位置與 A/B 判讀。
4. 原失敗案例、相關邊界與回歸驗收；尚缺證據。

尚未理解程式時先用 S9；工具／建置失敗用 S1；領域證據明確後轉 ROS S2、PIO S4、併發 S5、DMA S6、演算法／wire 格式 S7。詳細短卡與案例見同目錄 `index.md`。

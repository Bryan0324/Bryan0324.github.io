# S10｜邏輯分析與 Debug

## 短提示卡

```txt
請依我貼的程式、規格與真實結果分析debug；命令由我執行，不假稱測過。
先固定一筆失敗案例，沿輸入→驗證→分支/迴圈→狀態更新→輸出找第一個偏離預期的位置；崩潰行不一定是根因。針對證據查邊界、型別/單位、提前返回、跨次初始化、別名/生命週期，不列無關猜測。
原因已確定就給最小修正；否則最多3個候選，各附證據/缺漏，只選一個能區分原因的觀察，寫插入位置與A/B結果的意義。不要憑症狀重寫整檔、改唯讀測試或放寬題目規格。
只給：①偏離點與依據 ②一個修改或檢查 ③原失敗案例＋相關邊界/回歸驗收。標明推導、已驗證與待驗證；缺資料先問最關鍵一項。

需求／預期的依據／可改範圍：
語言、平台、目錄與原命令：
最小輸入、預期、實際／traceback：
相關宣告、函式與呼叫順序：
每次／第二次／高負載才錯：
已試修改與結果：
```

## 什麼時候選這張

| 情況 | 入口 |
|---|---|
| 只是看不懂一段程式 | [S9 程式解讀](../ncku-code-reading/#短提示卡) |
| 指令、import、compile、link、upload 失敗 | [S1 建置](../ncku-build-debug/#短提示卡) |
| 能執行，但例外、錯分支、第二次錯、沒有輸出，原因尚未定位 | **S10** |
| 已知是排序、hash 或 wire bytes 不符 | [S7 正確性](../ncku-algorithm-check/#短提示卡) |
| 已有 ROS、PIO、race、DMA 證據 | 對應 S2／S4／S5／S6，帶目前案例與已驗證事實 |

S10 是跨函式與執行路徑的通用定位流程；領域規格明確後再交專門技能。每輪只處理一個可驗收問題。

## 第一步：把「錯了」變成可重現案例

固定目前程式版本、執行目錄與命令；記下同一筆輸入、預期／依據、實際結果與完整相關 traceback。只貼 `FAIL` 不足以判斷算法、環境或測試入口哪裡出錯。

- 沒有預期答案：先問規格或可信 reference，不能自己改定義讓目前輸出算正確。
- 只在第二次錯：保留同進程的完整呼叫順序，分兩次啟動程式可能掩蓋狀態問題。
- 偶發錯：記錄 ID、時間順序、buffer 擁有者與負載；縮小案例時保留競態成立的條件。
- crash／例外：保留實際存取的型別、索引、容量與呼叫鏈，不只修最後報錯那行。

## 第二步：找第一個偏離點

用短表：`階段｜應有值／不變條件｜觀察值｜證據來源`。沒有量到的值標未知，不把推測補進「實際」欄。

1. 輸入是否就是預期那筆？ID、長度、型別、bytes、單位是否一致？
2. 驗證條件是否接受／拒絕錯對象？分支是否走錯？迴圈是否少一筆或多一筆？
3. 區域／全域／static 狀態是否在正確時機初始化？操作是改原物件還是副本？
4. 是否忽略返回碼、提前 return、漏 publish／return，或還沒完成就讀結果？
5. 最早能確認的不一致在哪個呼叫邊界？往前縮小範圍，而不是一次檢查整個專案。

C/C++ 已出現越界／未定義行為時，不能推定後續會固定得到某值。先定位非法操作與必要前提；主機 sanitizer／debugger 只在平台有支援且題目允許時使用，不能套到所有韌體。

## 第三步：證據不足才做區分實驗

候選表最多三列：`候選原因｜支持證據｜尚缺／可反駁觀察`。選一個能讓候選得出不同預測的動作。

例如有資料輸入卻沒有輸出：在 callback 入口、驗證失敗 return 前、publish 前記錄同一 ID 的簡短訊息。入口都沒出現先查上游；入口有、驗證失敗紀錄有，先對照驗證條件；到 publish 前但沒結果，再查發布返回碼與下游。
不要只說「加 log」：要給精確插入點、記哪些值，以及 A/B 如何決定下一步。競態下大量 log 可能改變時序，不能因加 log 後不重現就說已修好。

若程式與反例已足以證明原因，不必為了湊流程再做不必要的診斷。

## 微型案例：每次呼叫應獨立，第二次卻累加前一批

規格：每次只回傳該批總和。這是示範用失敗程式：

```python
total = 0

def batch_sum(values):
    global total
    for value in values:
        total += value
    return total
```

同一進程依序呼叫 `[2,3]`、`[7]`，可由程式推導結果為 5、12；題目預期為 5、7。第一個偏離點在第二次呼叫進入時，total 仍為 5，違反每批從 0 開始的需求。這不是編譯問題，也不需要先換加總算法。

最小修正：將函式內 `global total` 改成 `total = 0`，讓每次呼叫使用區域累積值。原失敗序列應變 5、7；同進程再測空輸入→0、同一批連叫兩次→相同結果，以及負值。這些是預期驗收，需由執行者回貼實際輸出。

## 固定輸出與停止條件

1. **症狀／第一個偏離點**：引用實際輸出或明確程式路徑。
2. **已確認根因／候選**：說清證據強度，不把相關性當因果。
3. **一個修改或觀察**：指定函式／區塊與執行位置；保留介面與可改範圍。
4. **驗收**：原失敗輸入、相關邊界、已通過案例；跨次狀態測試必須同進程連續執行。

原案例與相關回歸通過才結束該修正；沒測的列待測。兩次無效修改後回到最後可用版本，重新檢查假設與第一個差異，不繼續疊 patch。功能正確後再轉 S8 量效能。

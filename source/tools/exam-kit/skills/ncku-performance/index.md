# S8｜正確率優先的效能優化

## 短提示卡

```txt

區分發送/收到/完成/正確吞吐；提高發送率可能增加丟包。async工作要等真正完成再計時。多subscriber不自動分工；Python加thread不保證CPU運算加速；縮鎖不能移出必要共享操作；雙buffer需清楚所有權。demo pthread搬運時間不能代表真DMA。
```

## 工作契約

先看今年題目的評分公式，不沿用歷屆門檻。沒有基準與正確性資料時，先量測，不先大改。
每次只提出一項最有依據的變更，保留可回復的正確版本與允許修改範圍。
推估速度標為推估，沒有實際計時／judge 就不能宣稱加速或得分提升。

## 執行步驟

1. 寫出正確率門檻、每項功能分、效能分公式與計時區間。確認部分分是否有相依條件。
2. 若正確數未達門檻，先交 S2/S5/S6/S7；不得把錯誤更快送出去當成優化。
3. 固定資料集與版本，記錄送出／收到／完成／正確數、elapsed、有效吞吐與錯誤。
4. 沿資料路徑定位瓶頸：host 供給→transport→callback/queue→compute→DMA/PIO→publish→judge。
5. 只選一個瓶頸假設，設計能區分原因的 A/B 實驗；每組使用一致的資料與計時規則。
6. 變更後先確認正確，再比較速度；若差異接近量測波動，重複足以判斷的少量試驗。

## 知識卡

- 發送率、接收率、計算完成率、正確結果吞吐是不同數字。送更快可能只增加 backlog、丟包或超時。
- 量 async DMA／背景工作要等真正完成；只量 start 函式會得到誤導性的短時間。
- 本 demo 搬運引擎用 pthread，且每筆 nanosleep；其時間不能外推真 DMA 的吞吐或成本。
- 多 subscriber 不會自動負載平衡。兩塊板都收同 topic 可能重複算同筆；先查分派與 ID。
- 單執行緒 rclpy executor 的長 callback 會阻塞其他事件。Python CPU-bound 純 Python 工作也不能假設加 thread 就線性加速。
- 縮鎖前先分析共享不變條件；把共享讀寫搬到鎖外不叫優化。
- DMA＋CPU 重疊需獨立工作與明確 buffer 所有權；雙 buffer 不能讓 CPU 覆寫仍在傳輸的那一塊。
- 每筆 printf、序列化、配置／釋放也可能是瓶頸；先證明，再減少。
- 若只有佔總時間20%的區段能無限加速，整體上限只有1.25倍。用比例估算避免把時間花在小區段。
- FIFO、通道、buffer、CPU 都有限；不能假定把 queue 加大就能提高穩態吞吐。

## 操作選擇表

| 證據 | 一次只做的實驗 | 成功判準 |
|---|---|---|
| 上游送得少，下游常閒置 | 小幅提高發送率 | 正確吞吐上升且不增加缺失 |
| 提速後丟資料／延遲暴增 | 降回上個穩定速率，檢查 queue 與處理時間 | 找到供給／處理能力交界 |
| 時間主要花在每筆 log | 減少非必要 log，保留錯誤輸出 | 同正確率下耗時下降 |
| worker 大量等鎖 | 分離 thread-local 計算，保留必要共享更新 | 同結果且等待／總耗時下降 |
| CPU 等搬運、存在獨立工作 | 用明確所有權安排重疊，必要時雙 buffer | 端到端時間改善且連續多輪正確 |
| 算法本體最耗時 | 先選規格等價的計算簡化 | 主機 oracle 與整體 judge 都通過 |

## 微型判讀

原本100筆輸入，100筆正確，用2秒；改後100筆輸入，只60筆正確，用1秒。
若題目要求至少90筆正確，改後即使正確/秒看似較高也不達門檻。先恢復正確性，不繼續提高發送率。

## 固定輸出

1. **目前是否有資格優化**：對照正確率門檻。
2. **瓶頸假設＋證據／還缺什麼量測**。
3. **一項變更**：預期影響、修改位置、可能影響的正確性條件。
4. **A/B 紀錄表**：版本、送出、收到、正確、耗時、有效吞吐。
5. **保留或回退判準**：由真實數字決定，不以模型推估判勝。
